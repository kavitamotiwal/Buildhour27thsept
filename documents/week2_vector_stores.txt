Week 2 Lecture Notes: Vector Stores and Similarity Search

VECTOR STORAGE

A vector store is a database optimized for similarity search over embeddings. Alongside each
vector it stores metadata, typically the source file and the page or section the text came
from. That metadata is what makes a citation real rather than decorative: when the system
answers a question, it can point the reader at the exact place in the document the answer
supports.

Embedding vectors should be normalized before they are written. Once vectors are unit length,
similarity comparisons are consistent across runs, and a score recorded during a threshold
calibration still means the same thing the next day.

SIMILARITY SEARCH

A search embeds the query with the same model used at index time, then compares the query
vector against every stored vector and returns the highest scoring ones. This is an exhaustive
scan, sometimes called brute-force or flat search. It is accurate and predictable, which is why
it is the right choice for a corpus small enough to hold in memory.

Approximate methods such as HNSW build a graph of nearby vectors and traverse it instead of
scanning everything. They trade a small amount of accuracy for a large speedup once the corpus
grows past a few hundred thousand vectors. For a course-sized corpus, approximate indexing adds
tuning surface and recall risk with no meaningful gain.

TOP-K

The number of chunks returned to the model is usually four. Fewer gives the model too little
context and makes multi-part questions unanswerable. More adds irrelevant text, which measurably
degrades answer quality because the model tends to blend a relevant passage with a distracting
one. The useful range for a grounded system is narrow, and it should be recorded in the
configuration rather than hard-coded.

REBUILDING THE INDEX

Ingestion should overwrite the index rather than append to it. An append leaves chunks from a
previous version of the corpus in place, and the resulting answers cannot be reproduced or
explained. For a corpus small enough to embed in under a minute, rebuilding from scratch is
cheaper than tracking deletions.

Because ingestion is deterministic, running it twice over an unchanged corpus must produce an
identical index. A manifest recording the embedding model, the chunking parameters, the chunk
count, and a hash of the source files makes that property checkable instead of assumed.
